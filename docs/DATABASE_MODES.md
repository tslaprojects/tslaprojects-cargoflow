# Режимы данных: 🧪 Демо-база и 🗄️ Реальная база

CargoFlow работает с двумя полностью изолированными наборами данных. Режим выбирается на странице входа
(«🧪 Демо-база» / «🗄️ Реальная база»), фиксируется **сервером** в сессии и меняется только серверным переключением.

|                 | REAL                             | DEMO                                                            |
| --------------- | -------------------------------- | --------------------------------------------------------------- |
| Подключение     | `DATABASE_URL`                   | `DEMO_DATABASE_URL`; пусто — та же СУБД, схема `cargoflow_demo` |
| Метка схемы     | `cargoflow:real`                 | `cargoflow:demo`                                                |
| Данные          | рабочие данные компаний          | сгенерированный демо-мир (`npm run seed:demo`)                  |
| Identity/сессии | **здесь** (единая система входа) | только зеркальные записи пользователей (без паролей)            |

## 1. Архитектура

```
Запрос ─► route() / getCurrentActor()
            │  сессия (cookie cf_session → таблица Session в REAL) → session.dataMode
            ▼
     runWithDataMode(mode)   ── AsyncLocalStorage (API, jobs, скрипты)
     bindRenderDataMode(mode) ─ React cache() (серверные компоненты, RSC)
            ▼
     prisma (Proxy) ─► dbFor(currentDataMode()) ─► PrismaClient REAL | DEMO
```

- `src/lib/db/data-mode.ts` — тип `DataMode`, `runWithDataMode`, `bindRenderDataMode`, `currentDataMode`.
- `src/lib/db/data-mode-config.ts` — откуда брать подключение для режима (`dataModeConfig`), проверка, что DEMO ≠ REAL.
- `src/lib/db/prisma.ts` — единый провайдер:
  - `prisma` — клиент **базы режима текущего запроса** (бизнес-логика пишет как раньше, без `if (mode)`);
  - `authDb` — всегда REAL (identity, сессии, сброс пароля, приглашения);
  - `dbFor(mode)` — явный клиент режима (seed, плановые задачи, служебный код).
- Каждый клиент подключается с `search_path` своей схемы — raw SQL (`FOR UPDATE`, `nextval`) тоже изолирован.
- Кеш настроек платформы (`settings.service`) ведётся отдельно по режимам. Других глобальных кешей данных нет;
  после переключения режима клиент делает полную перезагрузку (`window.location.assign`) — состояние UI не смешивается.

## 2. Аутентификация и сессия

- Одни и те же email и пароль работают в обоих режимах: пароль проверяется **только** по REAL.
- `POST /api/auth/login` принимает `dataMode: "real" | "demo"` (по умолчанию `real`; иное значение — 422).
  Сервер проверяет готовность демо-базы (иначе 503 `SERVICE_UNAVAILABLE`, а не тихий вход в другую базу)
  и создаёт сессию с `Session.dataMode`.
- Режим запроса берётся **только** из серверной сессии. Тело, query, заголовки и cookie клиента режим не меняют
  (покрыто тестами: `tests/integration/data-modes.test.ts`, `tests/e2e/data-modes.spec.ts`).
- `POST /api/auth/data-mode` `{ dataMode }` — переключение после входа: новая сессия (новый токен), прежняя отзывается,
  событие пишется в аудит. В интерфейсе — индикатор режима в шапке (🧪 Демо / 🗄️ Real), по клику — подтверждение.
- Для страницы входа браузер помнит последний выбранный режим (`localStorage`, только как значение по умолчанию переключателя).

## 3. Роль ≠ режим

- Блокировка, удаление, роль платформы (`PLATFORM_ADMIN`) — всегда из REAL. Правка зеркальной записи в демо-базе
  не делает пользователя администратором; блокировка в REAL сразу закрывает и демо-сессию.
- Права в компании считаются как обычно (`permissionsForMembership`), но по членству в базе режима.
- При входе в демо (`provisionDemoIdentity`) пользователь получает зеркальную запись с тем же `id` и членство
  в ключевой демо-компании **того же типа и с той же ролью**, что и в REAL:
  грузовладелец → «Demo Cargo Kazakhstan», перевозчик/диспетчер/водитель → «Demo Trans Logistics»,
  экспедитор → «Demo Forwarding». Водителю назначается активный рейс демо-перевозчика.
- Демо-аккаунт без компаний в REAL (`*@cargoflow.demo` после очистки реальной базы) в демо занимает место своего
  персонажа seed с тем же email: те же компании и роли, профиль водителя с его рейсами, лента уведомлений.
- Если демо-база пересоздана, пока пользователь в системе, рабочее пространство восстанавливается при следующем запросе.

## 4. Точки входа

| Точка входа                                      | Режим                                                   |
| ------------------------------------------------ | ------------------------------------------------------- |
| 115 API-маршрутов через `route()`                | из сессии                                               |
| Серверные страницы (RSC) через `getCurrentActor` | из сессии                                               |
| Вход, регистрация, приглашения, сброс пароля     | REAL (identity)                                         |
| Webhooks платежей, топливных карт, телематики    | REAL (внешние провайдеры работают с реальными данными)  |
| `POST /api/system/jobs/secure-deal`, планировщик | по очереди для REAL и DEMO (DEMO — если база загружена) |
| Server Actions                                   | в проекте не используются                               |

## 5. Демо-генератор

`prisma/demo/` — детерминированный генератор (`mulberry32`, ключ `DEMO_SEED_KEY`, «сейчас» = `DEMO_SEED_DATE`):

- 40 клиентов, 16 перевозчиков (+ компании сценариев), 20 машин и 20 водителей (одна машина на обслуживании,
  один водитель неактивен, часть свободна);
- ≈100 грузов (черновики, опубликованные, торги, отменённые) и ≈70 перевозок во всех статусах:
  задержанные, на границе и таможне, срочные, крупные и мелкие, доставленные, закрытые, отменённые;
- ставки, договоры (с подписями), чаты, история статусов, трекинг (≈50 перевозок, точки по маршруту),
  документы (PDF-заглушки), уведомления (прочитанные и новые, свежие и старые).

Плюс сценарии `prisma/seed.ts` (демо-аккаунты, безопасная сделка, следующий рейс, топливо).
Персональные данные — вымышленные, домены `*.cargoflow.demo`.

```bash
npm run db:migrate:all     # миграции REAL и DEMO + метки схем
npm run seed:demo          # загрузить демо-базу, если она пуста (идемпотентно)
npm run seed:demo:reset    # очистить демо-базу и загрузить заново
npm run db:modes           # куда указывают режимы, метки схем
```

## 6. Защита реальной базы

`seed:demo` останавливается с `ERROR: Demo seed can only run against DEMO database.`, если:

- `DEMO_DATABASE_URL` указывает на ту же СУБД/базу/схему, что `DATABASE_URL` (учётные данные не важны);
- у целевой схемы нет метки `cargoflow:demo` (метку ставит `db:migrate:all`; схема с меткой `cargoflow:real` не перемечается);

Seed выполняется внутри `runWithDataMode("demo")` и пишет только через клиент DEMO; очистка (`TRUNCATE`)
ограничена `current_schema()` демо-подключения. Одновременный запуск нескольких seed исключён advisory-lock.

### Очистка реальной базы от демо-данных

Прежний seed грузил демо-данные в основную базу. Скрипт `scripts/purge-demo-from-real.ts` удаляет их:
демо-компании (номер `DEMO-…` и только участники `*cargoflow.demo`) со всеми данными и файлами в хранилище,
уведомления и сессии демо-аккаунтов. Учётные записи демо-аккаунтов остаются (вход единый), журнал аудита не меняется,
компании с реальными участниками не трогаются. Одна транзакция; повторный запуск ничего не делает.

```bash
npm run db:purge-demo              # сухой прогон: что будет удалено
npm run db:purge-demo -- --apply   # удалить
```

## 7. Запуск в контейнере

`scripts/docker-start.sh`: миграции обеих баз и метки → при `DEMO_SEED=1` фоновая загрузка демо-базы (если пуста) → `next start`.
Учётные записи для входа живут в REAL: на демо-стенде это демо-аккаунты сценариев (`*@cargoflow.demo`) или
зарегистрированные пользователи.

## 8. Как добавлять функциональность

- Бизнес-данные — через `prisma` из `@/lib/db/prisma`: режим подставится сам. Не создавайте свои `PrismaClient`.
- Identity и сессии — через `authDb` (или сервисы `auth.service`).
- Новый API-маршрут — через `route()`. Новый webhook/внешний вход без сессии — явно `runWithDataMode("real", …)`.
- Новая плановая задача — цикл по `DATA_MODES` с `runWithDataMode`.
- Новый глобальный кеш данных — ключ по `currentDataMode()`.
- Новые таблицы попадают в обе базы автоматически: `db:migrate:all` применяет те же миграции.

## 9. Ограничения

- Приглашения в компанию создаются и принимаются в REAL; в демо-режиме ссылка приглашения ведёт в реальный контур.
- Лента уведомлений пользователя в демо при первом входе копируется у персонажа seed с той же ролью в той же компании;
  дальше она живёт своей жизнью (`seed:demo:reset` — заново).
